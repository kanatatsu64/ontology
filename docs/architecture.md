# アーキテクチャ概要

この文書は現時点のシステム像を共有するためのものであり、具体的な技術選定を確定するものではありません。確定した判断は [ADR](adr/README.md) を正とします。

## コンテキスト

```text
┌──────────────────┐       ┌──────────────────────────┐       ┌──────────────────┐
│ 入力アプリ／      │       │ データプラットフォーム     │       │ 活用アプリ         │
│ コネクター         │──────▶│                          │◀──────│                  │
└──────────────────┘  API  │ Ontology + Data + Policy │  API  └──────────────────┘
                           └──────────────────────────┘
```

周辺アプリはデータプラットフォームの内部ストレージへ直接アクセスせず、公開された API 契約を通じて更新・参照します。

## 概念モデル

- **Entity**: 支出、取引先、口座、カテゴリなど、ドメイン内で識別される対象。
- **Property**: 金額、通貨、発生日、表示名など、Entity が持つ型付きの属性。
- **Link**: 「支出が取引先で発生した」「支出がカテゴリに分類された」など、Entity 間の型付きの関係。

オントロジーの定義（スキーマ）と、その定義に従う実データ（インスタンス）は区別します。識別子、型、制約、時間、履歴、出所をどのように表現するかは今後 ADR で決定します。

## 境界と責務

### データプラットフォーム

- オントロジー定義とその変更を管理する。
- Entity、Property、Link の整合性を維持する。
- 更新・検索・参照の API 契約を提供する。
- 認証された主体に対して認可を適用する。

### 周辺アプリ

- 特定の入力元または利用目的に最適化した体験を提供する。
- 公開 API のみに依存し、プラットフォームの永続化方式に依存しない。
- 入力固有の形式を、共有されたドメインの意味へ対応付ける。

## 未決定事項

API 方式、永続化モデル、整合性境界、イベント連携、モノレポか複数リポジトリかを含む技術的事項は未決定です。ユースケースと品質特性を明確にしたうえで、ADR に選択肢、決定、影響を記録します。
