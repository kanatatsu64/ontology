# 0005: migration 生成における差分の比較元

- 日付: 2026-09-06
- 意思決定者: プロジェクト
- 関連 ADR: 0002, 0004

## コンテキスト

環境に依存せず、YAML の意味の変更から migration を再現可能に生成する必要があります。

## 用語

| 用語 | 定義 |
| --- | --- |
| schema snapshot | migration 生成時点のオントロジー構造を正規化して保存した記録。 |
| 正規化済み IR | 表記上の違いを除き、意味を一意にした現在のオントロジーの内部表現。 |
| digest | file の内容が同じかを確認するために算出する固定長の値。 |
| transaction | 複数の変更をすべて成功またはすべて不成立として扱う単位。 |

## 決定

- version 付きの決定的な JSON snapshot と現在の正規化済み IR を比較します。初回は空 snapshot を使い、接続先 DB は比較元にしません。
- 差分を型、Property、Link の意味的な変更列へ分類してから PostgreSQL SQL を生成し、分類不能または transaction 外の操作では停止します。
- migration は一意な連番と変更前後の snapshot digest を持ち、既存 file を上書きしません。
- migration の編集者は、適用後 schema を新 snapshot と一致させる責任を負います。

## 検討

### D-1: 差分の比較元

#### 判断基準

- DB 接続なしで生成できること
- YAML の順序や省略表記を変更と誤認しないこと
- CI と local で同じ結果になること

#### 選択肢

- **正規化 snapshot:** 意味を比較できるが、形式の version 管理が必要になる。
- **前版 YAML:** 単純だが、表記差を除去しにくい。
- **接続先 DB:** drift は拾えるが、環境により結果が変わる。

#### 採用

**正規化 snapshot**を選びます。初回は空 snapshot と比較し、接続先 DB は入力にしません。

### D-2: snapshot の内容

#### 判断基準

- 意味的な変更を漏れなく比較できること
- 同じ ontology から同じ bytes を得られること
- 形式を将来移行できること

#### 選択肢

- **version 付き決定的 JSON:** diff しやすいが、migration 処理が旧形式を読む必要がある。
- **Rust binary serialization:** 小さいが、人がレビューしにくく実装へ密結合する。

#### 採用

**version 付き決定的 JSON**を選びます。時刻、絶対 path、comment、定義順を含めません。旧形式は現行 IR へ正規化して比較します。

### D-3: 差分から SQL への変換

#### 判断基準

- 変更の意図を SQL 生成前に検査できること
- 推測できない変更を安全に停止できること
- transaction 単位を明確にできること

#### 選択肢

- **意味的な変更列を経由:** 実装は増えるが、分類と SQL を分離できる。
- **snapshot から直接 SQL:** 短いが、比較と dialect が密結合する。

#### 採用

**意味的な変更列を経由**します。型・Property・Link の追加、削除、変更を分類し、分類不能または transaction 外操作では停止します。

### D-4: 生成後の migration

#### 判断基準

- 手書き data 移行を保持できること
- 既存 migration の履歴を書き換えないこと
- snapshot と最終 schema の一致を追跡できること

#### 選択肢

- **新規 file だけ生成:** 再生成は明示的になるが、手修正を保護できる。
- **常に上書き:** 操作は簡単だが、手修正を失う。

#### 採用

**新規 file だけ生成**します。一意な連番と変更前後の snapshot digest を記録し、編集者が適用後 schema の一致に責任を持ちます。

## 影響

並行 PR の rebase 後は最新 snapshot から migration を明示的に再生成し、再レビューします。
