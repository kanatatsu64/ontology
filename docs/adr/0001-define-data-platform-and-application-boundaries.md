# 0001: データプラットフォームと周辺アプリの責務境界

- 日付: 2026-09-06
- 意思決定者: プロジェクト
- 関連 ADR: なし

## コンテキスト

複数の支出入力元と活用方法を、共通のデータモデルへ接続する境界を定めます。

## 用語

- **データプラットフォーム:** 複数の周辺アプリで共有するモデル、データ、アクセス制御を管理する仕組み。
- **周辺アプリ:** 特定の入力元または利用目的を担い、データプラットフォームを利用するアプリケーション。
- **API:** 周辺アプリがデータプラットフォームを操作するための公開された契約。
- **Entity / Property / Link:** 対象、対象が持つ情報、対象間の関係を表すオントロジーの基本概念。

## 決定

共通データプラットフォームと目的別の周辺アプリを分離します。Entity、Property、Link とアクセス制御はプラットフォームが管理し、周辺アプリは API だけを介して更新・参照します。DB への直接アクセスは許可しません。

## 検討

### D-1: データとアプリケーションの責務

#### 判断基準

- 入力元と利用方法を独立して追加できること
- データの意味と制約を一か所で管理できること
- アプリごとの変更範囲を限定できること

#### 選択肢

- **単一アプリ:** 初期構成は単純だが、機能とモデルが密結合する。
- **アプリごとのデータストア:** 自律性は高いが、同期と意味の統一が必要になる。
- **共通プラットフォーム:** API 運用は増えるが、共通モデルで連携できる。

#### 採用

**共通プラットフォーム**を選びます。Entity、Property、Link とアクセスをプラットフォームが管理し、周辺アプリは目的別の入出力を担います。

### D-2: 境界を越えるアクセス方法

#### 判断基準

- 保存方式を周辺アプリから隠蔽できること
- 契約と互換性をレビューできること
- 認可を迂回できないこと

#### 選択肢

- **API のみ:** 契約管理は必要だが、境界を強制できる。
- **DB 直接アクセスも許可:** 実装は速いが、保存方式と権限へ密結合する。

#### 採用

**API のみ**を選びます。物理配置、process 分割、repository 構成はこの ADR では決めません。

## 影響

API の互換性とプラットフォーム障害を複数アプリにまたがって管理する必要があります。
