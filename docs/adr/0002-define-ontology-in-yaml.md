# 0002: オントロジー定義の原典と生成物の位置付け

- 日付: 2026-09-06
- 意思決定者: プロジェクト
- 関連 ADR: 0001

## コンテキスト

DB と API を一貫して生成するため、人と機械が扱える一つの原典が必要です。

## 決定

- Git 管理する YAML をオントロジー定義の唯一の正とします。
- SQL migration、schema snapshot、API 仕様、API interface を同じ PR に commit します。
- 生成物の手修正は SQL migration だけに許可し、その他は再生成します。
- 生成は固定 toolchain と repository 内の入力だけで決定的に行い、CI で再生成差分を検査します。

## 検討

### D-1: オントロジー定義の原典

#### 判断基準

- 人が記述し差分をレビューできること
- 機械的に厳密な検証ができること
- Git だけから状態を再現できること

#### 選択肢

- **YAML:** 読み書きしやすいが、利用する構文を制限する必要がある。
- **JSON:** 厳密だが、手書きには冗長になる。
- **DB:** 実行時変更に向くが、Git 上のレビューと再現が難しい。

#### 採用

**YAML**を選びます。秘密情報と環境固有値は含めません。

### D-2: 生成物の保管

#### 判断基準

- PR で YAML と結果を同時にレビューできること
- tool を持たない利用者も API 仕様と migration を参照できること
- 生成漏れを検出できること

#### 選択肢

- **すべて commit:** 差分は増えるが、レビューと参照が容易になる。
- **CI artifact のみ:** repository は小さいが、履歴と参照性が下がる。

#### 採用

**すべて commit**を選びます。CI は再生成差分がないことを検査します。

### D-3: 生成物の手修正

#### 判断基準

- YAML を唯一の正として維持できること
- schema だけでは表せない既存データ移行を記述できること

#### 選択肢

- **migration だけ許可:** data 移行を補えるが、編集者が最終 schema を保証する必要がある。
- **全生成物を許可:** 柔軟だが、YAML と乖離する。
- **全生成物を禁止:** 再現性は高いが、複雑な data 移行を扱えない。

#### 採用

**migration だけ許可**します。他の生成物は次回生成で置換します。

## 影響

生成は固定 toolchain と repository 内の入力だけで決定的に行う必要があります。
