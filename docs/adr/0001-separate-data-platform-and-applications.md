# 0001: データプラットフォームと周辺アプリを分離する

- 日付: 2026-09-06
- 意思決定者: プロジェクト
- 関連 ADR: なし

## コンテキスト

支出には手入力や外部明細など複数の入力元があり、集計、可視化、予算管理など複数の利用方法があります。個別アプリが独自にデータの意味と保存方式を持つと、連携のたびに変換が必要になり、意味や履歴の一貫性を保ちにくくなります。

一方で、あらゆるユースケースを単一アプリへ集約すると、機能同士が密結合し、独立した変更と検証が難しくなります。

## 決定

Entity、Property、Link を管理する共通データプラットフォームと、目的別の周辺アプリに分離します。周辺アプリによる更新と参照は、プラットフォームが公開する API を介して行います。周辺アプリからプラットフォームの内部ストレージへ直接アクセスすることは許可しません。

この判断は論理的な責務と契約の境界を定めるものであり、ネットワーク上の配置、プロセス分割、リポジトリ構成、実装技術は決定しません。それらは要件に基づく後続 ADR で扱います。

## 検討した選択肢

### 単一の支出管理アプリ

- 利点: 初期構成が単純で、アプリ内の機能を直接連携できる。
- 欠点: 入力・活用機能とデータモデルが密結合し、用途が増えるほど変更影響が広がる。

### アプリごとに独立したデータストアを持つ

- 利点: 各アプリが用途に最適なモデルと技術を選べる。
- 欠点: データが重複し、同期、意味の統一、権限管理が難しい。

### 共通データプラットフォームと周辺アプリに分離する

- 利点: データの意味とガバナンスを共有しながら、用途別のアプリを独立して構築できる。
- 欠点: API 契約、互換性、プラットフォーム運用という追加の複雑性が生じる。

## 影響

### 良い影響

- 入力元と利用方法を、共有データモデルを介して組み合わせられる。
- オントロジーとアクセス制御をプラットフォームで一貫して扱える。
- 周辺アプリを用途に合わせて独立に進化させられる。

### 悪い影響・トレードオフ

- API とオントロジーのバージョニングおよび互換性管理が必要になる。
- プラットフォーム障害が複数アプリへ影響するため、信頼性設計が重要になる。
- 分散境界をまたぐ処理では、整合性、遅延、エラー処理を明示的に扱う必要がある。
